# 参考标准指南

本文档定义了 SRS 文档生成时需遵循的两项核心标准：**GB/T 22239-2019（等保二级）** 和 **IEEE 830-1998**。生成 SRS 时，应将标准要求映射到对应章节。

---

## 一、GB/T 22239-2019 — 网络安全等级保护基本要求（等保二级）

### 1.1 标准概述

GB/T 22239-2019 是《信息安全技术 网络安全等级保护基本要求》国家标准，等保二级为"指导保护级"，适用于一般信息系统。

> 标准发布日期：2019-05-10，实施日期：2019-12-01

### 1.2 等保二级核心安全要求与 SRS 章节映射

| 等保要求项 | 等保二级要求 | SRS 对应章节 | 文档中应体现的内容 |
|------------|-------------|-------------|-------------------|
| **身份鉴别** | 用户身份标识和鉴别，口令复杂度要求，登录失败处理 | §2.1 用户角色、§3.1 用户认证、§4.3 安全需求 | 用户登录功能含密码策略（≥8位字母+数字）、锁定机制（连续5次失败锁定30分钟） |
| **访问控制** | 基于角色的访问控制，最小权限原则 | §2.1 用户角色、§3.N 权限矩阵 | 角色权限矩阵表，明确各角色可访问的页面和功能 |
| **安全审计** | 记录关键操作日志，日志不可删除/修改 | §3.N 系统管理、§11 附录 | 审计日志功能需求（含日志字段：用户、操作、资源、时间、IP）；附录列出审计事件清单 |
| **通信完整性** | 通信过程中数据完整性校验 | §4.3 安全需求 | TLS 1.2 传输加密；API 签名校验（可选） |
| **通信保密性** | 会话和敏感数据传输加密 | §4.3 安全需求、§5 技术架构 | Cookie 设置 HttpOnly+Secure；全站 HTTPS |
| **数据完整性** | 数据库存储数据完整性保障 | §4.3 安全需求、§6 数据需求 | 数据库约束（主键、外键、唯一索引）；事务 ACID 保障 |
| **数据保密性** | 敏感数据存储加密 | §4.3 安全需求 | 密码使用 BCrypt/PBKDF2 不可逆存储；个人隐私字段脱敏 |
| **数据备份恢复** | 定期备份，备份数据保护 | §4.2 可靠性需求 | 每日全量备份策略，保留周期（≥7天），恢复演练要求 |
| **软件容错** | 输入校验、故障隔离 | §4.2 可靠性需求、§3 各功能需求 | 表单输入校验规则；服务故障不影响其他模块 |
| **资源控制** | 会话超时、并发限制 | §4.1 性能需求 | Session 超时时间（30分钟）；并发连接数限制 |

### 1.3 等保二级验收标准模板

生成 SRS 第 10 章"安全验收"时，应包含以下等保二级专项验收项：

| 等保项 | 验收标准 | 测试方法 |
|--------|----------|----------|
| 身份鉴别 | 密码策略生效，登录锁定机制正常，Session 超时自动登出 | 手工测试 |
| 访问控制 | 低权限用户无法访问高权限功能，接口返回 403 | 权限矩阵遍历测试 |
| 安全审计 | 关键操作（登录、创建、修改、删除）自动记录，日志不可删除 | 操作后检查审计表 |
| 通信保密 | 全站 HTTPS，Cookie 含 Secure+HttpOnly 标志 | 浏览器 DevTools + 抓包 |
| 数据备份 | 数据库每日自动备份，备份文件可恢复 | 模拟备份恢复流程 |
| 软件容错 | 异常输入有校验提示，单模块故障不影响整体 | 边界值测试、故障注入 |

### 1.4 等保二级 SRS 写作规则

1. **安全需求必须可验证**：每项安全指标须对应明确的测试方法和通过标准
2. **审计范围须明确**：在功能需求中标注"须记录审计日志"的操作
3. **密码策略须量化**：不能只写"密码复杂度要求"，应写"≥8位，含大写字母、小写字母、数字中至少两类"
4. **备份策略须具体**：须写明备份频率、保留周期、恢复流程
5. **最小权限原则**：角色权限矩阵必须体现"仅授予完成任务所需的最小权限"

## 二、IEEE 830-1998 — 软件需求规格说明推荐实践

### 2.1 标准概述

IEEE 830-1998 是 IEEE 发布的《软件需求规格说明推荐实践》（IEEE Recommended Practice for Software Requirements Specifications），是国际公认的 SRS 编写标准。

> 标准编号：IEEE Std 830-1998，已被 ISO/IEC/IEEE 29148:2011 取代，但其核心理念仍是 SRS 编写基础。

### 2.2 优质 SRS 的八大特征

IEEE 830 定义了优质 SRS 的 8 个核心特征，生成文档时必须确保满足：

| 特征 | IEEE 830 定义 | SRS 编写时的落实方法 |
|------|---------------|---------------------|
| **正确 (Correct)** | 每项需求都是软件应满足的真实需求 | 每个 FR 须有明确的前置条件和业务规则，避免主观描述 |
| **无歧义 (Unambiguous)** | 每项需求只有一种解释 | 使用表格定义状态、枚举值；避免"可能""大概""较好"等模糊词 |
| **完整 (Complete)** | 包含所有重要需求，含功能、性能、接口、设计约束 | 使用第 3 章"功能需求"验证清单，逐模块核对 |
| **一致 (Consistent)** | 需求之间不冲突 | 同一术语全文一致；状态流转规则不自相矛盾 |
| **按重要性分级 (Ranked)** | 每项需求标注重要性和稳定性 | 使用 [M]/[S]/[O] + P0-P3 双重标记体系 |
| **可验证 (Verifiable)** | 存在有限成本的过程可验证需求是否满足 | 每项需求对应第 10 章的一个验收项 |
| **可修改 (Modifiable)** | 需求变更时能保持结构和风格一致 | 版本控制表记录每次变更；需求编号独立于章节编号 |
| **可追踪 (Traceable)** | 每项需求可追溯到其来源 | FR 编号贯穿功能需求 → 接口需求 → 验收标准 |

### 2.4 IEEE 830 写作规则

生成 SRS 时，严格遵循以下 IEEE 830 写作规范：

1. **使用"应（shall）"表达强制需求**：每个 FR 描述中使用"系统应…"句式
2. **避免使用"将（will）""可能（may）""可以（can）"**：这些词引入歧义
3. **每条需求独立编号并唯一标识**：FR-XXX-NNN 满足此要求
4. **需求与验收一一对应**：每个 FR 必须在第 10 章有对应的验收项
5. **区分功能需求与设计**：第 3 章只描述"做什么"，不描述"怎么做"；"怎么做"放在第 5 章
6. **外部接口必须完整定义**：第 7 章的每个接口须含方法、路径、输入、输出、异常
7. **文档控制中应引用 IEEE 830**：在 1.5 参考文档中标注 IEEE 830-1998

### 2.5 IEEE 830 质量检查清单

生成 SRS 后，对照以下检查清单逐项验证：

- [ ] 每个 FR 是否使用"应"（shall）句式表达？
- [ ] 是否有任何模糊词汇（可能、大概、约、较好、尽量）？
- [ ] 每个 FR 是否有唯一编号？
- [ ] 是否有需求相互矛盾？特别是状态流转规则。
- [ ] 每个 FR 是否在第 10 章有对应的验收标准？
- [ ] 外部接口（API）是否定义了所有异常情况？
- [ ] 是否区分了"需求"和"设计"（第3章 vs 第5章）？
- [ ] 非功能需求是否量化（带数字指标，非定性描述）？
- [ ] 设计约束是否全部列出？
- [ ] 文档控制表是否记录了所有版本变更？

## 三、两项标准的协同应用

### 3.1 标准互补关系

```
IEEE 830-1998                    GB/T 22239-2019
┌─────────────────────┐          ┌─────────────────────┐
│ SRS 编写方法论        │          │ 安全需求最低标准       │
│ • 怎么写 SRS          │          │ • 安全需求必须包含什么   │
│ • 需求如何组织         │ ── 互补 ┤ │ • 安全指标如何量化      │
│ • 什么是好需求         │          │ • 审计/加密/备份要求     │
└─────────────────────┘          └─────────────────────┘
         │                                  │
         └──────────┬───────────────────────┘
                    ▼
          ┌─────────────────────┐
          │  高质量、合规的 SRS   │
          │  • 格式规范 (IEEE)   │
          │  • 安全合规 (等保)   │
          │  • 可验证、可追踪    │
          └─────────────────────┘
```

### 3.2 章节级协同映射

| SRS 章节 | IEEE 830 要求 | 等保二级要求 | 生成时的协同策略 |
|----------|:------------:|:----------:|----------------|
| 1.5 参考文档 | 列出所有参考标准 | — | 固定包含 GB/T 22239-2019 和 IEEE 830-1998 |
| 2.3 设计约束 | 列出全部约束 | 信创合规（如适用） | 等保二级达标作为一条设计约束 |
| 3.1 用户认证 | 功能需求，可验证 | 身份鉴别 | 密码策略 + 锁定机制，含量化指标 |
| 3.N 权限 | 功能需求 | 访问控制 | 完整权限矩阵，最小权限原则 |
| 3.N 审计 | 功能需求 | 安全审计 | 审计日志不可删除/修改 |
| 4.2 可靠性 | 属性需求 | 数据备份恢复 | 备份策略 + RTO/RPO 指标 |
| 4.3 安全 | 属性需求 | 全部安全要求 | 来源于等保二级的全量安全指标 |
| 10.3 安全验收 | 每项需可验证 | 每项需可测评 | 等保专项验收项 + 对应测试方法 |

## 四、标准引用模板

在 SRS 文档的 1.5 参考文档章节，应固定包含以下条目：

| 编号 | 文档名称 | 版本/编号 | 说明 |
|:----:|----------|-----------|------|
| REF-01 | 《信息安全技术 网络安全等级保护基本要求》 | GB/T 22239-2019 | 等保二级安全要求基准 |
| REF-02 | 《软件需求规格说明推荐实践》 | IEEE 830-1998 | SRS 编写方法论标准 |

在 1.6 文档约定或脚注中说明：

> 本文档遵循 IEEE 830-1998 定义的 SRS 质量特征（正确、无歧义、完整、一致、分级、可验证、可修改、可追踪）编写，安全需求参照 GB/T 22239-2019 等保二级要求制定。
